# 金蝶 K3「BOM单」批量录入经验总结

> 场景：把一张 BOM 用量表里的「物料号 + 用量」两列，逐行录入已打开的 K3「BOM单 - 新增」界面。
> 只填 **商品代码** 和 **用量** 两列，其它列（单位、子项类型、商品属性、发料仓库/仓位、使用状态）由 K3 自动带出。
> 结束时**不点保存**。

---

## 0. 启动顺序（每次开工先做这两件事，做完才准录入）

**第 1 件：平均左右分屏 —— Agent 界面占左半屏，K3 BOM 占右半屏。**
调用 Windows 自带的贴靠（Aero Snap）：`SetForegroundWindow` → `sleep 0.5` → `Win+←`（左窗口）/ `Win+→`（K3）→ `GetWindowRect` 校验 → 不合格回退 `SetWindowPos` 精确 50/50。
一键脚本：`python _snap_split.py`。实测结果 左窗口 `(0,0,960,1032)`、K3 `(960,0,1920,1032)`。
窗口按**类名**找，不按标题找：操作端窗口=`Chrome_WidgetWin_1`、K3=`ThunderRT6FormDC`。

**第 2 件：向右拨 K3 表格底部的横向滚动条，直到列标题出现「用 量」。**
分屏后 K3 只有 960px 宽，「用量」列默认在视口外（可见列只到「使用状态」）。

> ⚠️ **旧版「连续右拨 4 次」是错的，已废弃（第 2 轮自检实测结论）**：横滑条点一次位移很大，右拨 4 次会把滑条拨过头，用量列被移出视口，固定一个偏右的 `X_QTY`（如 1722）会静默命中「备注」列 —— 这是第 1 轮自检 `columns_visible/calib_hit/single_row/multi_row` 全 FAIL 的根因。

✅ 正确做法 = `ensure_view(dlg, pid)`：先 `hscroll_home()` 点左箭头归零 → **右拨 1 次** → `auto_calibrate(write=False)` 动态标定 → 点 `X_QTY` 验证 `is_qty()` → 成功才写回 `_k3_calib.json`。
- 归零态(right=0)：只有 `aid200 left=1036` 铺满整行，**没有 aid201**（用量在视口外）。
- **归零 + 右拨 1 次 = 标准视口**：`aid201 left=1392`(用量) / `left=1451`(损耗率) / `left=1729`(备注)；`aid200 left=1043`(商品代码)。注意不同列宽配置下这组数字会变，以 `calib` 实测为准。
- 右拨 2 次及以上：`aid201 left=1274`(用量) / `left=1376`(损耗率)，焦点残留错乱。

⭐ **aid 200/201 不是列唯一**：多个文本列都是 `aid=200`，多个数值列（用量/损耗率）都是 `aid=201`。判列必须 **`(aid, rect.left)` 双条件**（商品代码=aid200 里 `rect.left` 最小、用量=aid201 里 `rect.left` 最小）；**绝不靠 4 位小数**（空行用量显示 `'0'` 无小数点，损耗率显示 `'0.00'`）。判据从「`automation_id == 201`」升级为 `(aid=201, rect.left == QTY_LEFT)`。

一键脚本：`python _k3_fill.py calib` → `OK right_step=1 X_CODE=1051 CODE_LEFT=1043 X_QTY=1669 QTY_LEFT=1661 groups200=[1043,1611] groups201=[(1661,'0'),(1763,'0.00')]`（列宽配置不同则数字不同）。横向滚动只平移列，**不改行号**。

做完这两件事，**窗口尺寸与列可见范围都已经变了，旧坐标全部作废**，必须按 3.2 重新标定后再录入。

## 0.1 铁律（每次操作前先看这五条）

1. **时刻检测 ERP 是否弹窗，及时处理 —— 这是最重要的一条**。
   K3 是 VB6 + 第三方表格控件（SPR32A70），几乎任何非常规操作（点空白行、输入无效代码、按键导航、滚动过头、切换列）都会弹 `#32770` 模态框。
   弹窗期间主窗口**所有** `type_keys` 都会抛 `pywinauto.base_wrapper.ElementNotEnabled`，看起来像「按键失灵 / 点不中 / 程序卡住」，其实只是被模态框挡住了；
   而且弹窗会自动**抢走焦点并让表格跳行**，你后续按旧坐标点的位置全错 —— 这是本项目前期反复「点了没反应」「数据错位」的根本原因。
   → 因此**每个动作之后都要检测**（不是出错才检测）：
     统一封装 `check_dialog(pid)`：`EnumWindows` 找 `#32770` + 同 PID + 可见 → `EnumChildWindows` 读文字 → **按按钮文字优先点「否」**（`CLOSE_BTN_PRIORITY = ("否","取消","确定","是")`）。
     ⚠️ 旧版固定点 `(rect.left+330, rect.top+155)`（约 (1100,605)）作废：实测「当前单据已经改变，是否保存单据？」弹窗 `(347,450,733,629)` 里该坐标落在「取消(&C)」上，甚至可能落到「是(&Y)」触发误保存。所有按键改走 `safe_keys`（弹窗期 `type_keys` 抛 `ElementNotEnabled` 时先清弹窗再重试）。
     调用时机：`click` 之后、`type_keys` 之前、`{ENTER}` 之后 `sleep` 完、滚动之后、切换行列之后。
     一旦检测到弹窗：先关掉 → **重新截图或 `focused()` 重新定位当前单元格** → 再继续，绝不能沿用旧坐标。
2. **不要点保存**（工具栏 `保存` 在 y≈76，x≈1041~1053）。误点等于写库。
3. **不要用方向键导航行**（用户明确否决）。滚动只允许两种：鼠标滚轮 / 点竖滚动条箭头（右下方箭头 `(1915,907)` 下滚、`(1917,470)` 上滚；横向 `(974,917)` 左、`(1882,917)` 右）。
4. **每次 `{ENTER}` 之后必须重读 `focused().rect.top` 重新锚定行**。在「当前可视区最后一行」提交商品代码后，K3 **一定会自动上滚 16 px 并把焦点右移到商品属性列**；沿用旧 y 会写到下一行，静默出错（详见 5.4）。
5. **「用量」列默认可能在视口右侧外**，先看列标题有没有「用 量」，没有就点底部横向滚动条右箭头，然后重新标定 `X_QTY`（详见 5.3）。

## 2. 定位窗口（不要硬编码 HWND！）

K3 每开一张 BOM 就是**新 HWND**，重开窗口后旧 HWND 全部失效（本次从 2034932 变成 1246804）。

```python
def find_bom_window(title_kw="BOM单 - 新增"):
    res = []
    def cb(h, _):
        try:
            if win32gui.IsWindowVisible(h) and title_kw in win32gui.GetWindowText(h):
                res.append((h, win32process.GetWindowThreadProcessId(h)[1],
                            win32gui.GetWindowText(h), win32gui.GetWindowRect(h)))
        except Exception:
            pass
    win32gui.EnumWindows(cb, None)
    return res
```

注意 K3 同时存在多个 `BOM单 - *` 窗口（新增 / 修改 / 多级展开），**必须按标题 + 可见性筛选**，别操作错窗口。
`win32gui.GetWindowThreadProcessId` 不存在，要用 `win32process.GetWindowThreadProcessId`。

## 3. 表格坐标（窗口 "BOM单 - 新增" 最大化的常见布局）

以「商品代码 | 商品属性 | 辅助属性 | 单位 | 子项类型 | 用量 | 损耗率 | 使用状态 | 发料仓库 | 发料仓位」这套列为例（屏幕绝对坐标）：

| 元素 | 坐标 |
|---|---|
| 列标题行 | y ≈ 472 |
| 第 1 数据行 | y = 502，行高 **16 px** → `row_y(n) = 502 + 16*(n-1)` |
| 商品代码列 | x ≈ 1065（控件 rect x=1036..1131） |
| 用量列 | x ≈ 1330（控件 rect x=1321..1422） |
| 表格可视底 | y ≈ 924（约 25 行） |
| 竖向滚动条 | x ≈ 1917；上箭头 y≈470，下箭头 y≈915 |
| 横向滚动条 | y ≈ 917；左箭头 x≈968，右箭头 x≈1922 |
| **保存按钮（禁点）** | x≈1047, y≈76 |

⚠️ 不同 BOM 单 / 不同列宽下坐标会变（本次新开的 BOM000000 列布局就不同：商品代码列 x≈1000..1127，后面是 商品名称 / 规格型号）。
**必须先截图或 `focused()` 反查 rect 校准，不能盲抄旧坐标。**

### 3.1 分屏（左窗口 / K3 右）与坐标重标定

想把编辑器放左边、K3 放右边同时看，用 Windows 自带的**贴靠（Aero Snap）**最省事：

| 动作 | 快捷键 | 效果 |
|---|---|---|
| 贴左半屏 | `Win + ←` | 窗口占左半，高度铺满工作区 |
| 贴右半屏 | `Win + →` | 窗口占右半 |
| 最大化 | `Win + ↑` | —— |
| 取消贴靠 | `Win + ↓` | 还原为浮动窗口 |

脚本 `_snap_split.py` 已封装：

```python
key(0x5B)                     # VK_LWIN 按下
key(vk) / key(vk, up=True)    # VK_LEFT=0x25 / VK_RIGHT=0x27
key(0x5B, up=True)            # 松开 Win
```

要点与坑：

- **必须先 `SetForegroundWindow(hwnd)` 再发键**，且中间 `sleep 0.5`；否则 Win+← 会贴到别的窗口上。
- 用 `keybd_event` 而不是 `SendInput` 更省事（`SendInput` 需要构造 `INPUT`/`KEYBDINPUT` 结构体）。
- K3 是 VB6 `ThunderRT6FormDC`，**贴靠成功后它是"最大化"状态**（`IsZoomed` 为真）；此时 `SetWindowPos` 改大小会无效，必须先 `ShowWindow(SW_RESTORE)`。
- Aero Snap 有时只贴了第一个窗口（第二个不发键或焦点没抢到）。最稳的做法是：**先试 Win+← / Win+→，再用 `GetWindowRect` 校验；不合格直接回退 `SetWindowPos` 精确 50/50**（视觉等价，脚本用 `SPI_GETWORKAREA` 读工作区，不写死分辨率；实测 1920×1080 + 48px 任务栏 → 左 `(0,0,960,1032)`、K3 `(960,0,1920,1032)`）。
- 找窗口别用标题子串硬匹配（K3 的标题是 GBK 显示成乱码，按标题子串匹配 有时因全角破折号/编码问题为 False）。**按窗口类名匹配最稳**：操作端窗口 = `Chrome_WidgetWin_1`，K3 = `ThunderRT6FormDC`。

### 3.2 ⚠️ 窗口尺寸一变，所有坐标全部失效

这是分屏后必须立刻做的事：**重新标定**。实测同一张 BOM000000：

| | 最大化 1927 宽 | 50/50 分屏 960 宽 + 右拨 1 次 |
|---|---|---|
| 商品代码列 x | 1070（控件 left=1036） | **1090（控件 left=1043）** |
| 用量列 x | 1371（控件 left=1274） | **1400（控件 left=1392）** |
| 损耗率列 x | — | 1830~1860（控件 left=1451） |
| 备注列 x | 1740 | 1742~1800（控件 left=1729）|
| 可见列 | 到「存在替代关系」 | 到「使用状态」（右侧被裁） |

标定方法：点一个已知格 → 读 `focused()` 的 `rect.left`（这是控件左边界，列 x 取它 +20~60）→ 再用 `rect.top` 反推行高。

标定结果持久化到脚本目录下的 `_k3_calib.json`，`_k3_fill.py` 启动时自动加载：

```json
{"X_CODE": 1090, "X_QTY": 1400, "ROW_H": 16, "GRID_TOP": 492, "GRID_BOTTOM": 900,
 "SCROLL_UP": [1908, 468], "SCROLL_DOWN": [1908, 891],
 "HSCROLL_LEFT": [987, 908], "HSCROLL_Y": 908, "HSCROLL_RIGHT_X": 1891,
 "CODE_LEFT": 1043, "QTY_LEFT": 1392}
```

`python _k3_fill.py calib 520` 可以横扫一行自动探测（步长 6px，逐点 click 读 automation_id），但**很慢**（整行要 1 分多钟）且容易被弹窗打断，日常更推荐手动点两三个格子读 `rect` 后直接写 json。

分屏还有一个副作用：**列可见范围变小**。原本能看到的 `发料仓库/发料仓位/备注` 可能被裁掉，录入时只需要 `商品代码` 与 `用量`，所以无影响；但如果要核对发料仓位，就点横向滚动条右箭头临时看。

### UIA 事实（很重要）

- K3 **只把「当前获得焦点的单元格」暴露给 UIA**，其它单元格一律不可枚举 → 无法靠 UIA 遍历表格。
  `_k3_cells.py` 枚举 automationId 200/201 只能拿到 1 行。
- 商品代码单元格：`automationId=200`，`class=SPR32A70EditHScroll`
- 用量单元格：`automationId=201`，`class=SPR32A70Float`，`window_text` 带 4 位小数（`22.0000`）
- `SPR32A70_SpreadSheet` 不支持任何 UIA Pattern（ScrollPattern / GridPattern / ValuePattern 全 `NoPatternInterfaceError`）→ **无法程序化滚动、无法读全表**。
- 判定「点中了哪个单元格」：遍历 `dlg.descendants()` 找 `has_keyboard_focus()` 的元素，看 `(automation_id, window_text, class_name, rect.top)`。

## 4. 单行录入流程（已验证有效）

```
click(X_CODE, row_y)        # 命中代码单元格，automation_id 应为 200
type_keys("^a")             # 清空（首次为空也无害）
type_keys(code)             # 例如 1.99.001
type_keys("{ENTER}")        # 提交 → K3 自动带出 单位/属性/仓库/仓位
sleep(1.2); check_dialog()  # 必查！代码不存在/为空会弹框
click(X_QTY, row_y)         # 命中用量单元格，automation_id 应为 201
type_keys("^a"); type_keys(qty); type_keys("{ENTER}")
sleep(0.5); check_dialog()
```

要点：
- **必须先 `click` 命中单元格再输入**；`type_keys` 只在单元格进入编辑态时生效。
- 输入后**必须 `{ENTER}` 提交**，否则下一次 click 会把没提交的内容丢掉。
- 点击落在**空白行**上会弹「请输入 物料代码」（内容是 `Static|请输入 物料代码` + `Button|确定(&O)`），点「确定」即可，不是错误。
- 点击落在**已有数据行**的代码格，会把原值选中，直接输入会覆盖 —— 但**大量实测表明打字偶发会拼接**（`1.99.0011.99.002`），所以一律先 `^a`。
- 若 `^a` + 输入仍拼接，退路：用 UIA `set_value`（ValuePattern）直接写控件值。

## 5. 滚动（踩坑最多的一块）

被否决/无效的方式：

| 方式 | 结果 |
|---|---|
| `{DOWN}` 方向键 | 用户明确否决；且第 2 次必弹「请输入 物料代码」 |
| 表格内直接发 `MOUSEEVENTF_WHEEL` | 无效（表格不响应，或只滚 1 行且焦点丢失） |
| UIA ScrollPattern | K3 不支持该 Pattern |
| `win32gui` 找 scrollbar 子窗口 | `scroll-like elements: 0`，滚动条不是独立子窗口 |

**有效方式（用户认可）**：

- **点竖滚动条箭头**：`click(1917, 470)` = 向上滚；`click(1917, 915)` = 向下滚。每次约 1~2 行，稳定、不弹窗。
- **鼠标滚轮**：前提是**先 click 表格内部拿到焦点**，再在同一位置发 `MOUSEEVENTF_WHEEL`；否则无效。滚轮一格约 3 行，**容易滚过头**（曾从行 25 直接滚到行 26-50）。
- 滚过头不要慌：合计行（`50.25` 这种）等于已录入行之和，可用来判断数据是否完好；再点上箭头滚回来即可。
- 滚回顶部后 `row_y(n)=502+16*(n-1)` 才成立；滚动状态下首行 y=502 对应的是**当前顶行**，必须重新标定行号。

### 5.3 横向滚动（一开始可能看不见「用量」列）

K3 的 BOM 明细列很宽，默认视口常常只显示到 `子项类型`，**「用量」列在视口右侧之外**。这就是「一开始看不见用量列」的原因，不是列被隐藏了。

- 横向滚动条在表格底部：`y ≈ 917`，左箭头 `x ≈ 974`，右箭头 `x ≈ 1882`（**50/50 分屏后**右箭头变成 `x ≈ 1893`，左箭头 `x ≈ 975`；y 仍约 917）。
- 点**左箭头** = 往左（回到 `序号|商品代码|商品名称|规格型号` 那一头）；点**右箭头** = 往右（把 `用量|损耗率|使用状态|发料仓库|发料仓位` 带进视口）。每次约 1 列宽。
- 实测（BOM000000）：左箭头 ×3 → 视图变成 `序号|商品代码|商品名称|规格型号`；右箭头 ×3 → 恢复 `序号|商品代码|商品属性|单位|子项类型|用量|…`，行 1-25 可见，合计不变。
- 实测（BOM000000 分屏 960 宽）：右箭头 ×4 → 列序变成 `序号|商品代码|商品名称|规格型号|商品属性|单位|子项类型|用量|损耗率|使用状态`，`用 量` 曾被推到 x≈1722；**同一位置在只拨 1 次时是「备注」列** —— 这就是必须每次都重读 `rect.left` 的原因。
- 一键：`python _k3_fill.py hscroll right 4`。
- **横向滚动只改变列的位置，不改变行的 y**。但一旦横向拖动过，`X_CODE / X_QTY` 全部要重新标定（列左移/右移了）。
- 判断「用量列是否在视口内」：截图看列标题行有没有 `用 量`。没有就先点右箭头，再重新标定 X_QTY。

### 5.4 ⭐ 提交商品代码后 K3 会自动滚动（最阴的坑）

现象：在**当前可视区最后一行**输入商品代码并按 `{ENTER}` 后，K3 会**自动向上滚动正好一行（16 px）**，同时把焦点移到同行的**下一列**（`商品属性`，left=1193）。此时如果按原来的 y 去点「用量」列，就会点到**下一行**的用量格 —— 数据写到错行，且不报错。

实测数据（BOM000000，1927×1039 窗口）：

```
click(1070, 886)  -> focused = ('200','', 'SPR32A70EditHScroll', top=879, left=1036)   # 命中最后可见行代码格
type "1.99.003" + {ENTER}
focused           -> ('200','', 'SPR32A70EditHScroll', top=863, left=1193)
SCROLL_DELTA_PX   = 879 - 863 = 16   # 正好一行
```

错误后果（实测）：

```
用旧 y=879 点用量列 -> ('201','0','SPR32A70Float', top=878, left=1274)   # 命中下一行，空值
用新 y=863 点用量列 -> ('201','1.0000','SPR32A70Float', top=862, left=1274) # 命中当前行，正确
```

**触发条件（三个都要满足）**：
1. 目标行是**当前可视区最后一行**（下面还有空白行）；
2. 该行的**下一行必须是空白行** —— 如果下一行已经有代码，K3 不需要让位，就不会滚（这就是「填完 26 行后复现不出来」的原因）；
3. 用 `{ENTER}` 提交，不是 Tab、不是点别处。

**复现实验步骤**（用户提示的做法）：滚动到明细最末尾的空白行区域，让目标行成为最后可见行且下一行空白 → 在该行代码格输入任意合法物料号 → `{ENTER}` → 观察表格上滚一行、焦点跳到 `商品属性`。

⇒ **铁律：每次 `{ENTER}` 之后都要重新读 `focused().rect.top`，用新 top 推算同行其它列的 y，绝不复用点击前的 y。** 具体做法：

```python
f = focused(dlg)                  # f = (auto_id, text, class, top, left)
y_row = f[3] + 8                  # 同行任意列点击用的 y（行中部）
# 校验仍然命中同一行：
click(X_QTY, y_row)
f2 = focused(dlg)
assert f2[3] in (f[3], f[3] + 1), "行已漂移，重新锚定"
```

### 5.5 行号反推（不要盲目 row_y(n)）

- 只在**表格处于滚动条最顶端**时 `row_y(n) = 502 + 16*(n-1)` 成立。
- 一旦滚过、或录入过程中 K3 自动滚过，公式失效。此时用 `focused()` 的 `rect.top` 做**相对锚定**：先点一个已知行拿到 top，再 `y = top + 16*(n - known_row) + 8`。
- 序号列 `x ≈ 992` **不可选中**（点它 focused 不变），不能当行锚点。
- 最可靠的锚点是：`focused()` 返回 `automation_id` 是否等于预期（200=代码列、201=用量列）+ `rect.left`（1000..1131=代码列、1274..1421=用量列）。

### 5.6 滚动后如何判断数据没坏

底部的**合计行**（明细表下方、右侧）等于当前所有行用量之和。滚过头、弹窗跳行之后先看合计：
- 本次 36 行正确合计 = `77.25`（其中前 24 行 = 50.25）。
- 如果合计多了/少了一个已知值，就说明多录或丢了一行，按差值定位。

## 6. 弹窗处理（本次教训的核心）

- 检测：`EnumWindows` 找 `IsWindowVisible` 且 `class_name == "#32770"` 且 `PID == K3 的 PID`。
- 读文字：`EnumChildWindows` 抓 `Static` / `Button` 的 `GetWindowText`（pywinauto 的 descendants 经常返回空，Win32 更可靠）；中文乱码就写 UTF-8 文件再 cat。
- 已见到的弹窗：
  - `Static|请输入 物料代码` + `Button|确定(&O)` → 点在空行，点 (1100,605) 关掉。
  - `可能是：1、你没有权限查看...输入的代码:[xxx]在数据库中不存在或被禁用。是/否` → 代码不存在（批量粘贴时出现），点「否」(1100,605)。
- **弹窗存在时所有 `type_keys` 抛 `ElementNotEnabled`**。所以流程里每次 `sleep` 后都要 `check_dialog()`，而不是等报错再救。
- 弹窗关闭后主窗口可能**同时滚动/跳行**，必须重新截图或 `focused()` 重新定位。
