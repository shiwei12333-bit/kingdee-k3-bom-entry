# 标定手册：换机器 / 换分辨率 / 换 K3 版本后怎么重新校准

> 这套流程里所有点击都是**物理像素坐标**。窗口大小变、分屏比例变、列宽被拖动、DPI 缩放变、
> K3 补丁包换了列顺序 —— 任何一种都会让坐标失效。失效时脚本往往**不报错**，只是把数据写进
> 错误的格子。所以换环境第一件事永远是重新标定。

## 一、标定前的准备

1. 打开 K3，进入「BOM单 - 新增」，让明细表格完整显示出来。
2. 关闭所有会弹通知的程序（微信、QQ、邮件客户端、系统更新提示）。
3. 确认没有开启系统级缩放混合（右键 exe → 属性 → 兼容性 → 更改高 DPI 设置）。
4. 记下当前分辨率与任务栏高度。

## 二、第一步：分屏

```bash
cd skills/k3-bom-grid-entry/scripts
python _snap_split.py
```

它会读 `SPI_GETWORKAREA` 拿工作区，把操作端窗口放左半、K3 放右半，不写死任何分辨率。

**校验**：脚本最后会打印类似

```
left=(0, 0, 960, 1032) K3=(960, 0, 1920, 1032) FG=0x18a117c
```

- `left=` 是操作端窗口（Agent / 终端 / 浏览器宿主）的矩形
- `K3=` 是 K3 主窗口矩形
- 两者宽度应接近相等，`FG=` 应等于 K3 的 hwnd

若 `left=` 取错了窗口：设置环境变量指定标题关键字

```bash
export K3_LEFT_HINTS="WindowsTerminal,cmd"     # 逗号分隔，任一命中即选中
python _snap_split.py
```

## 三、第二步：让「用量」列进入视口

K3 明细表默认停在最左，**看不到「用量」列**。必须横向右拨一次。

- 横向滚动条：`rect = (977, 900, 924, 17)`，中心 y = **908**
- 右箭头 `(1891, 908)`、左箭头 `(987, 908)`

```bash
python _k3_fill.py hscroll right 1
```

> ⚠️ 这两组数字**不是猜的**：早期版本把 y 写成 917（在滚动条下边框之外）、x 写成 975（在左边界
> 977 之外），结果箭头从未被点中，视口永远卡在最左，连续 11 轮标定全部失败。

拨完后**必须截图确认列标题出现「用量」**，不能只看脚本返回值。

## 四、第三步：读列坐标

```bash
python _k3_fill.py calib
```

输出示例（1920 宽、50/50 分屏、横拨 1 次）：

```
OK right_step=1 X_CODE=1051 CODE_LEFT=1043 X_QTY=1669 QTY_LEFT=1661
   groups200=[1043, 1611] groups201=[(1661, '0'), (1763, '0.00')]
```

关键常量及其含义：

| 常量 | 实测值 | 说明 |
|---|---|---|
| `X_CODE` | 1090 | 商品代码列的点击 x |
| `X_QTY` | **1400** | 用量列的点击 x（⚠️ 不是 1740/1770/1800） |
| `QTY_LEFT` | 1392 | 用量列控件的 `rect.left` |
| `Y1` | 496 | 第一行数据行的 y |
| `ROW_H` | 16 | 行距（像素） |
| `PAGE_ROWS` | 24 | 每页录入行数 = 可见行数(25) − 1 |
| `SCROLL_UP` | (1908, 468) | 纵向滚动条上箭头 |
| `SCROLL_DOWN` | (1908, 891) | 纵向滚动条下箭头 |
| `HSCROLL_LEFT` | (987, 908) | 横向左箭头 |
| `HSCROLL_RIGHT_X` | 1891 | 横向右箭头 x |

标定结果写到 `scripts/_k3_calib.json`（已在 `.gitignore`，不入库）。

## 五、第四步：确认列身份（最容易错的一步）

横拨一次之后的列序（1920 宽、50/50 分屏）：

```
序号 999 │ 商品代码 1074 │ 商品属性 │ 辅助属性 │ 单位 │ 子类 │ 用量 1394 │ 损耗率 1467 │ 使用状态 1560 │ 发料仓库 1619 │ 发料仓位 1689 │ 备注 1742 │ 存在替代 1860
```

**三个陷阱**：

| x 范围 | 实际落点 | 后果 |
|---|---|---|
| 1400 附近 | ✅ 用量（`aid=201`, `left=1392`） | 正确 |
| 1742 ~ 1800 | ❌ **备注**（`left=1729`） | 把数量写成备注，用量仍是 0 |
| 1830 ~ 1860 | ❌ **损耗率**（`left=1451`） | 把数量当损耗率，BOM 总成本算错 |

而 `focused()` 在这三处可能都返回 `aid=201` —— 因为它读的是 UIA 陈旧缓存。
**不要靠返回值判断，靠截图看列标题。**

## 六、第五步：跑自检

```bash
python _k3_selftest.py --loop 3
```

10 个用例覆盖：窗口识别、分屏几何、前台归属、横滚几何、列坐标、首行 y、行距、页容量、坐标自洽、文档一致性。

期望结尾：

```
== FINAL: ALL GREEN ==
```

任何一项 FAIL 都说明标定参数与当前屏幕不一致，回到第三步重来。

## 七、常见标定失败原因

| 现象 | 原因 | 处理 |
|---|---|---|
| `calib` 连续报 `right_step=0` | 横向箭头没点中（y 或 x 落在滚动条外） | 用 UIA 读 `ScrollBar` 真实 rect，不要抄旧值 |
| `detect_columns` 认不出用量列 | 空白单据的用量值是 `''` 而非 `'0'`，被 float 过滤掉了 | 按 `aid==201` 且 `rect.left` 最小取，不做数值过滤 |
| `X_QTY` 每次都不一样 | 横扫采点时点到了不同列的格子，K3 又自动横滚 | 加几何自洽过滤：`left <= x <= left + 200` |
| 录入后全表空白 | 某处发了 `ESC`（= 取消该格输入） | 永不发 ESC，退编辑态点列标题空白 `(1890, 476)` |
| 第 2 行开始错位 | 提交代码后视口自动上滚 16 px 没被发现 | 每页写完重新读视口首行序号 |
| 出现 `1.99.0021.99.001`（两段代码被拼接在一起） | 编辑态未清空，新输入被**追加**拼接 | 点格后必须 `ctrl+a` → `DELETE` 再输入 |

## 八、换分辨率时的换算

若只是分辨率整体变化（DPI 不变），可以按比例粗算，再逐项截图校验：

```
x_new = x_old * (screen_width_new / 1920)
y_new = y_old * (screen_height_new / 1080)
```

但 **行距 `ROW_H` 和每页行数不会按比例变** —— 它们由 K3 的字体与表格行高决定，必须实测。
分辨率一变，`PAGE_ROWS` 很可能从 24 变成别的值，务必重新数一遍可见行数。

## 九、标定检查单

- [ ] 分屏几何打印正常，`FG` 等于 K3 的 hwnd
- [ ] 横拨 1 次后截图能看到「用量」列标题
- [ ] `calib` 输出里 `QTY_LEFT` 与截图里用量列左边缘对得上
- [ ] 手工点一次 `X_QTY, Y1`，截图确认光标所在格是**用量**而不是备注/损耗率
- [ ] `_k3_selftest.py --loop 3` 全绿
- [ ] `ROW_H` 与相邻两行 y 之差一致
- [ ] 数一遍可见行数，`PAGE_ROWS = 可见行数 − 1`
